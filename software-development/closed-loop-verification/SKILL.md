# 闭环验证协议 (Closed-Loop Verification)

> **来源：** 钱学森《工程控制论》第7章 — 反馈控制系统设计
> **核心理念：** 每完成一个任务 = 闭环结束，必须用比较器对比 "输出信号 y(t)" 和 "参考信号 r(t)"。

## 触发条件

任何以下任务完成后自动触发：
- 代码生成或修改（write_file / patch）
- 数据分析并输出结论
- 文件写入（报告、配置、脚本）
- 复杂的多步骤任务

## 协议步骤

### 1. 回读输出
用不同于生成路径的方式确认输出内容：
- 代码 / 文件 → `read_file` 回读关键段落
- 分析结论 → 自我复述核心数字和逻辑

### 2. 逐条对照需求
提取用户原始消息中的 **可验证约束**（功能要求、格式要求、数据指标、边界条件），逐条打勾。

### 3. 标注偏差
| 状态 | 含义 |
|------|------|
| ✅ | 完全满足 |
| ⚠️ | 有偏差但已自修正 |
| ❓ | 无法确定，需用户确认 |

### 4. 自修正或标记
- 能自己改的：立即改，标 ⚠️
- 需要用户决策的：标 ❓ 并说明选项

### 5. 输出验证报告（3-5 行，嵌入最终回复末尾）

## 输出格式

```
🔍 闭环验证:
✅ 需求 A — 已满足
✅ 需求 B — 已满足
⚠️ 需求 C — {偏差说明} → 已自修正
❓ 需求 D — {需要你确认的事项}
```

## 陷阱与误区

- ❌ 不要跳过验证直接汇报"完成了" — 闭环少了比较器就不是闭环
- ❌ 不要只验证表面（语法/格式），要验证语义正确性
- ❌ 用户说"可以"/"OK" ≠ 不需验证 — 那只是批准执行，不是确认结果
- ✅ 验证报告简短嵌入回复末尾即可，不必单独发一条消息
- ✅ 全部 ✅ 时可以简化为一句话 "🔍 闭环验证: 全部通过"

## 示例

用户："写一个计算斐波那契第 n 项的函数，要求处理 n=0 和 n=1 的边界"

```
... [代码输出] ...

🔍 闭环验证:
✅ 计算斐波那契第 n 项 — fib(n) 已实现
✅ 处理 n=0 — 返回 0
✅ 处理 n=1 — 返回 1
✅ 无额外需求遗漏 — 全部通过
```

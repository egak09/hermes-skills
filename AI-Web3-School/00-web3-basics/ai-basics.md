## 1. LLM（大语言模型）

### 一句话

一种通过海量文本训练出来的神经网络，输入一段文字，输出最可能接在后面的文字——没有"理解"，只有"预测下一个 token"。

### 具体例子

你问 ChatGPT "法国的首都是？"，它不是去查数据库然后告诉你"巴黎"，而是把这句话拆成 token 序列，然后计算下一个最可能出现的 token 是"巴"，再下一个是"黎"。

你现在用的 Hermes（然然），背后是 DeepSeek V4 Pro 这个 LLM。它对你说的话不是"想"出来的，是一个 token 一个 token "猜"出来的。只不过训练数据够大、参数够多之后，这种猜看起来像理解。

### 误区

> "LLM 会思考"  
> 不会。它没有内部状态、没有信念、没有记忆（除非外部系统给它）。你今天早上跟它说的话，下午它就"忘"了——除非有 context / memory 系统替你记住。LLM 本质是一个**无状态的函数**：输入 tokens → 输出 tokens。

### 使用边界

- LLM 擅长：模式识别、文本生成、代码补全、翻译、总结
- LLM 不擅长：精确数学、实时信息（除非接工具）、保持长期一致性（需要外部 memory）

## 2. Prompt（提示词）

### 一句话

你对 LLM 说的所有话——包括系统指令、用户消息、上下文注入——的通称。Prompt 决定了模型"看到什么"，从而决定了它"说什么"。

### 具体例子

然然的系统 prompt 里有你的个人信息、Windows 环境提示、工具使用规则、行为约束。这些你从来没打过字，但它们**每一轮都在模型看到的内容里**。

你的 prompt 不是只有你打的那句话。是：

```
[系统 prompt ~8000 tokens] +
[memory 注入 ~2000 tokens] +
[技能文档 ~5000 tokens] +
[对话历史 ~N tokens] +
"你的问题"
```

所以你问"帮我查一下 BTC 价格"，然然能回答"好的 Paradigme，我来查"——不是因为它聪明，是 prompt 里写了你的名字叫 Paradigme。

### 误区

> "Prompt 越详细越好"  
> 不全是。Prompt 也消耗 context window。你写一个 10 页的 prompt，可能把之前重要的对话历史挤出去了。**精准比冗长重要**。

## 3. Context Window（上下文窗口）

### 一句话

模型一次能"看到"多少文本的上限。超过这个上限的内容会被裁掉或压缩。这是你使用任何 LLM 时最需要理解的物理限制。

### 具体例子

DeepSeek V4 的上下文窗口具体多大取决于版本，主流在 128K tokens 左右。听起来很大——但如果一个 session 持续 80 轮对话，加上技能文档 + memory + 工具输出……很快就到头了。

然然的行为就是最好的例子：

- 对话长了会触发 **context compression**（压缩中间轮次）
- Memory 被限制在 2,200 字符，因为每一轮都注入 system prompt
- 技能文档不主动加载，而是按需调用 `skill_view()`——因为全塞进去 context window 就爆了

### 误区

> "128K 窗口够大，不用担心"  
> 你知道 128K tokens 是多少吗？大概一本 200 页的书。听起来很多——但你每一次工具调用的输出（比如一个 5,000 行的代码文件、一次 web search 的 30 个结果）都在吃窗口。**一个长 session 可能在 50 轮之内就吃掉一半窗口。** 窗口不是"一天用多少"，是"这一刻塞了多少"。

## 4. Workflow（工作流）

### 一句话

把一个大任务拆成多个步骤，每一步有明确的输入、输出和完成标准，按顺序或条件执行——和编程里的 pipeline 一个意思。

### 具体例子

妖币策略的扫描流程就是一个 workflow：

```
拉行情 → 形态识别 → OI/Vol 分析 → 评分 → ≥68? → 等下一根 K 线
                                              ↓ 否
                                          丢弃信号
```

这不是"AI 神奇地做出决策"，是一系列**确定的、可验证的步骤**。每一步的输出是下一步的输入。

### 误区

> "Workflow 就是 Agent"  
> 不是。Workflow 是固定的管道——A → B → C → D，每次都一样。Agent 是动态的——它自己决定下一步做什么。Workflow 像工厂流水线，Agent 像给你一个工具箱说"自己想办法"。

### 使用边界

| | Workflow | Agent |
|---|---------|-------|
| 流程 | 固定路径 | 动态决策 |
| 可靠性 | 高（可测试每一步） | 中等（取决于模型判断） |
| 适用 | 重复性任务（CI、定时报告） | 开放式任务（debug、研究） |
| 成本 | 低（不需要复杂推理） | 高（每步都调 LLM） |

## 5. Agent（智能体）

### 一句话

一个 LLM + 工具 + 循环决策的系统：它看到当前状态，决定调用什么工具，拿到工具结果，再决定下一步——直到任务完成或达到轮次上限。

### 具体例子

然然就是 Agent。你不是在跟一个"聊天机器人"聊天——你在跟一个**能读文件、能跑终端、能搜网页、能发消息、能调度 cron 的系统**对话。

典型的 Agent loop：

```
你: "帮我看看 BTC 价格"
  ↓
然然: { 调用 blockbeats 搜索 }
  ↓
然然: { 拿到 BTC 价格数据 }
  ↓
然然: "BTC 现在是 $87,342，24h 跌了 2.3%"

这就是：感知 → 决策 → 行动 → 反馈 → 再决策
```

### 误区

> "Agent 比 Workflow 高级，所以优先用 Agent"  
> 恰恰相反。如果你能写成一个固定的 workflow，就**不要用 Agent**。Agent 每一轮决策都要调 LLM，又慢又贵又可能出错。Workflow 确定、可测试、成本低。Agent 的价值在于**你事先不知道要做什么**的时候。

## 6. Tool Use（工具调用）

### 一句话

LLM 不直接执行操作，而是生成**结构化的函数调用参数**，由外部系统（Hermes 的 tool dispatcher）实际执行——LLM 是"大脑"，工具是"手"。

### 具体例子

你让然然"创建一个文件"——实际发生了什么：

```
然然（LLM）输出：
{
  "tool": "write_file",
  "path": "/path/to/file.md",
  "content": "..."
}

↓ 这不是 LLM 在写文件，这是 Hermes 的 tool system 在执行

Hermes 接收这个 JSON → 验证路径 → 安全检查 → 写入磁盘 → 
返回结果给 LLM → LLM 告诉你 "文件已创建"
```

你看不到这个过程。你以为然然在写文件。其实然然只是**告诉你 write_file 的参数应该是什么**。

同理：`terminal`、`read_file`、`search_files`——LLM 都在"说参数"，Hermes 在"执行"。LLM 本身没有文件系统访问、没有 shell、没有网络。

### 误区

> "AI 帮我执行了命令，所以 AI 有系统权限"  
> 没有。AI 只有"描述它想执行什么"的能力。真正执行的是宿主系统。如果宿主系统有安全策略（比如 Hermes 的 approvals.mode），危险命令会被拦截。**权限永远在工具层，不在 LLM 层**。

## 7. AI Coding（AI 辅助编程）

### 一句话

用 LLM 辅助写代码——不只是"生成一段代码"，包括理解代码库、Review PR、生成测试、修复 Bug、解释报错。

### 具体例子

你让然然帮你写妖币策略的 Python 脚本。这个过程不是"AI 生成一些代码然后复制粘贴"那么简单：

```
你: "帮我写一个函数，从 Binance 拉 5 分钟 K 线并计算成交量均线"

然然:
1. 加载 binance-trading skill → 了解 API 格式和代理配置
2. 加载 demon-strategy skill → 了解现有的评分逻辑
3. 搜索现有代码 → 避免重复造轮子
4. 写代码
5. 用正确的 Python 314 路径测试
6. 遇到 ImportError → 修复依赖
7. 测试通过 → 交付
```

这不是"代码补全"。这是**理解环境、读取上下文、写代码、测试、修复**的完整过程。

### 误区

> "AI 写的代码可以直接用"  
> 不能。AI 不知道你的运行时环境的所有细节（Python 版本、包版本、系统差异、隐藏的 bug）。永远需要**阅读、理解、测试**——至少跑一遍。

### 使用边界

- 适合：脚手架、重复性代码、测试用例、文档、重构
- 不适合：核心安全逻辑、加密算法、需要精确性能优化的热路径
- 铁律：**AI 写的代码，你读懂了才算你的代码**

## 8. Guardrails（护栏）

### 一句话

在 AI 系统执行操作前设置的限制和检查——"可以做 A，不能做 B，做 C 之前必须问"。

### 具体例子

然然的护栏有好几层：

| 层 | 例子 | 位置 |
|----|------|------|
| 系统 prompt | "所有文件只能存到 D:\\Hermes file" | prompt |
| Skill 约束 | "binance 交易必须过凯利公式" | skill docs |
| 工具层 | `rm -rf /` 需要确认 | approvals system |
| Memory 约束 | "技能使用原则：不得未经许可主动调用" | memory |
| 环境隔离 | 代理确保 API 走白名单 IP | network config |

每一层都在说同一件事：**你可以很能干，但有些事你不能干、有些事你干了要问我**。

### 误区

> "System prompt 里写了就行"  
> 不够。Prompt 是最弱的一层护栏——LLM 可能被越狱（jailbreak），可能理解错误，可能在长对话中忽略早期指令。护栏需要**多层防御**：prompt + 工具层权限 + 外部验证 + 人工确认。

## 9. Tracing（追踪）

### 一句话

记录 LLM 每一步在想什么、调了什么工具、拿到了什么结果、为什么做了这个决策——调试 Agent 的唯一手段。

### 具体例子

然然的一个完整 turn 的 trace 大概长这样：

```
[Turn 15] user: "帮我查一下 POL 的持仓"
  → LLM call #1: 决定调用 binance account.py
  → Tool result: { BTC: 0.12, ETH: 2.3, USDT: 5432, ... }
  → LLM call #2: "你的账户里有 5432 USDT，没有 POL 持仓"
  → Done. Tokens used: 2341 in, 89 out. Cost: $0.003

如果某一步错了（比如 ETH 余额显示为 0），你可以回溯：
  是 API 返回了错误数据？
  是 LLM 解析 JSON 时截断了？
  是之前某一步的上下文被压缩掉了？
```

没有 tracing 的话你只能猜。有了 tracing 你能**精准定位**问题在工具的哪一步、LLM 的哪一轮调用。

### 误区

> "Agent 出错了就换个模型"  
> 换模型不解决根本问题。90% 的 Agent 错误不在模型质量，在：工具返回格式不符合预期、上下文窗口不够导致早期信息丢失、prompt 有歧义、审批流程卡住。**Tracing 告诉你问题根源，换模型只是在瞎子摸象。**

## 10. Human-in-the-Loop / HITL（人机协同）

### 一句话

AI 不是全自动的。在关键决策点——涉及资金、隐私、不可逆操作——插入人工确认环节。AI 负责分析和建议，人负责拍板。

### 具体例子

妖币策略的 HITL 设计：

```
AI: 扫描 → 评分 → 推送通知 "SKYAI 110分，建议开仓"
你: 看一眼 → 判断市场情绪 → 决定开不开
开仓：你手动在 Binance 操作（AI 碰不到你的资金）
```

这跟自动交易机器人的区别：**最后按按钮的是你**。

同样地，然然在执行 `rm -rf`、`git push` 等操作前会弹确认。这不是多此一举——这是 **HITL 在工具层的体现**。

### 误区

> "HITL 降低了效率，应该追求全自动"  
> 看场景。推特自动发帖？可以全自动。汇款 10 万 USDT？永远不应该全自动。HITL 的原则是：**如果一个错误会导致不可逆的损失，就必须有一个人清醒地确认。** 效率再重要也没有本金重要。

## 📝 复核说明

### 我的复核方式

1. **去 AI 腔**：每一段我都问"这句话是我会说的还是 ChatGPT 会说的"。比如把"通过海量语料训练的自回归语言模型"改成"输入文字，输出文字，没有理解，只有预测"。

2. **用你见过的东西举例**：不是编造 AWS Lambda 的假例子，而是用然然的行为、妖币策略的代码、你的 memory 约束、代理配置——这些都是你每天在用的东西。

3. **加入边界和限制**：AI 文档最容易犯的毛病是"什么都能做"。我在每个概念后面明确写了**不能做什么**：LLM 没有记忆、Agent 不如 Workflow 可靠、AI 写的代码不能直接用。

4. **交叉验证**：Context Window 的大小、Tool Use 的实现原理、Agent loop 的结构——这些不是我"猜"的，是从 Hermes 的实际行为（你每天看到的压缩提示、技能加载、审批弹窗）反推验证的。

### 没有用到的内容

我刻意省略了：
- 训练、微调、RLHF 等模型训练概念（你不需要训练模型）
- Transformer 架构细节（用 Agent 不需要懂 Attention）
- RAG 的通用框架描述（你用的是 Hermes 的 memory/skill 系统，不是理论 RAG）
- 过于学术化的定义（你不是在写论文）
